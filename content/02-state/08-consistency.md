# 两台设备看到不同的收藏，究竟哪份算数？

你在手机收藏了一篇文章，电脑上的收藏夹暂时还没出现它。并不一定是文章消失了，也可能是电脑还没取得新的记录。

当信息存在多处，或者几个人同时修改，就要安排它们怎样对上。**一致性关心的是：这些记录和显示，应当满足什么关系。**

## 复制方便使用，也带来时间差

假设手机和电脑都显示同一个收藏夹。手机发出收藏要求，服务端保存成功；电脑需要再次读取，才知道有了新收藏。保存和传播不是一个瞬间完成的动作。

产品可以允许电脑短暂显示旧结果，并随后刷新；也可以在某些操作中要求先确认最新记录。不同场景需要的保证不同。普通收藏允许短暂落后，最后一件库存的售卖则不能随意让两人都买走。

## 一件事有两步时，怎样避免只做一半？

想象一个示意性的积分转赠：给小林扣10分，再给小周加10分。若扣分后中断，另一边没有增加，两个人的总积分就少了。

先把这个虚构例子的数字固定下来：小林有100分，小周有20分，总共120分。我们希望转赠后变成90分和30分，总数仍是120。这条“转赠不凭空增加或减少积分”的要求，是人先确定的规则。

如果把扣分和加分当成两个独立保存动作，第一个保存成功、第二个失败，就会停在90分和20分。电脑没有读懂“这其实是一件事”，它只是按收到的两个动作分别做了。

程序需要明确告诉数据库：**把扣分和加分放进同一次事务，全部做成以后再提交**。可以沿着下面的过程看：

| 发生到哪里 | 这次修改处于什么状态 | 其他普通读取会得到什么 |
| --- | --- | --- |
| 开始之前 | 正式记录是100分、20分 | 100分、20分 |
| 事务内已扣10分，尚未加分 | 扣分仍是未提交的修改，不是独立完成的一笔转赠 | 不会把未提交的90分、20分当作已完成结果读走 |
| 加分成功，事务提交 | 两项修改一起成为正式结果 | 后续读取可以得到90分、30分 |
| 加分失败，事务撤销 | 本次未提交的修改取消 | 正式结果仍是100分、20分 |

数据库会管理尚未提交的修改，并保留按其机制恢复所需的记录。正常出错可以撤销；运行中断后也能按恢复规则处理未完成事务。并不是出错以后，再靠人从屏幕上猜应该补回多少分。把一组修改作为一个成功或失败的整体，叫**原子性**。

### 中断以后，数据库凭什么恢复？

以正常提供持久性保证的 PostgreSQL 为例，它会先把描述修改的日志可靠写下，再按提交要求确认成功。数据文件不一定在同一瞬间全部写完；如果随后中断，可以根据日志把应当保留的修改重新落实。这说明“已经提交”不是只在内存里放一个成功提示。

对于没有成功提交的事务，恢复和可见性机制不会让它的半份修改变成一笔已完成转赠。数据库怎样组织日志、旧版本和恢复步骤各有实现，你在这里先抓住提交这道分界：提交前还没正式完成，提交后才算这次修改已经成立。不同读取还可能看到先前的完整版本，具体由隔离规则决定。

事务也不替你决定业务是否合理。程序如果写成“扣10分、加20分”，全部成功照样不符合转赠规则；两个人同时扣同一账户，还需要相应的余额检查和并发控制。**事务保证的范围，要和你想一起完成的修改对上。**

假设还要发一封“转赠成功”的邮件。邮件已经发出去，数据库不能把收件箱里的邮件收回来。常见安排是：在同一事务里保存积分变化和一条“待发送通知”；提交后另一个程序读取通知并发送，失败再试。这样避免积分没转成却先发成功通知，但发送本身仍可能重复，需要用通知编号识别。跨系统合作的失败继续见[超时与重试](../05-reliability/17-failure.md)。

## 同时编辑，也需要明确处理办法

两个人都打开旧标题，一人改成“旅行记录”，一人改成“周末游记”。若后来的保存直接覆盖，前一个修改可能消失。

这类相互不兼容的修改叫**冲突**。系统要检测它，得留下比较依据，不能只收一个新标题就知道你是从哪个旧标题改的。

一种办法是给文章保留版本号。下面仍是教学示意，不表示所有软件都采用同一种做法：

1. 小林和小周打开文章，都拿到标题“旅行”和版本7。
2. 小林提交“旅行记录”，同时说明“我是在版本7上改的”。保存程序只有在当前版本仍是7时，才接受这次修改，并一起更新为版本8。
3. 小周随后提交“周末游记”，带来的仍是版本7。当前已经是8，保存程序拒绝直接覆盖，返回“文章已被修改”，并保留小周尚未保存的文字。
4. 页面并排显示当前标题和小周的草稿，让他重新选择。若他确认使用自己的标题，就以最新版本再次提交；也可以保留当前标题，或手动改成第三个标题。

比较版本和保存新内容必须作为一个不可被另一份保存插入的操作来执行。若先检查、隔一会儿再无条件保存，两次检查仍可能都通过，又回到互相覆盖的问题。

系统在这里发现了“你的修改基于旧版本”，**没有替两个人判断哪个标题更好**。不同段落的文字有时能合并，同一个标题的两种意思却未必能自动合并；产品也可以明确允许后保存者覆盖，但应让使用者知道这个规则。

## “正确”要用产品规则说明

一致性不只是“所有地方永远长得一模一样”。你在手机展开目录，通常无须让电脑也展开；共享收藏记录，却可能需要同步。

先确定哪些信息共享、哪些只是各自的临时选择，再规定何时需要一致、冲突怎样处理。这连接了[状态](06-state.md)、[时间与等待](../03-communication/12-time.md)和[失败](../05-reliability/17-failure.md)。

## 换成最后一件库存，应该怎样想？

虚构商店只剩一本书，两个人都在页面上看到“剩余1件”。这个显示可以已经过时，不能凭它直接生成两个成功订单。处理购买的程序要把“确认仍有库存、扣减库存、建立对应订单”协调好，让两个购买请求不能都占用同一件。

一个实现方向是：在同一事务范围里，只在库存仍大于零时扣减；真正扣减成功的请求才能建立订单，失败的请求显示售罄。具体还要按数据库的并发规则实现。它和收藏的差别在于：收藏列表暂时少显示一篇通常还能刷新，卖出并不存在的第二本书却破坏了产品规则。

因此遇到“一致性”，可以提出三类不同的问题：这里是显示还没更新，还是相关修改只做了一半，还是两个人争着修改同一份记录？它们都涉及正确关系，但不能靠一句“同步一下”解决。
