# API 是什么，为什么程序要通过它合作？

你到咖啡店说“要一杯拿铁”，店员知道这项服务需要什么信息、会交给你什么。如果你跑进后厨，对着每台机器随便操作，合作就很难稳定。

程序也需要清楚的交接方式：能要求对方做什么，要交哪些信息，能收到什么结果。**这套可用能力和交接约定，就是接口**。咖啡店只是帮助理解交接，真实程序交换的是结构明确的信息。

## 用收藏动作认识一个 API

假设文章服务提供“加入收藏”能力。其他程序调用它时，要给出用户和文章的身份信息；它返回“成功”“已经收藏”或“没有权限”等结果。

这就是一个供程序使用的接口，常见名字是 **API**。不只是 AI 公司有 API，操作系统、数据库、软件内部模块都可以提供程序接口。

它把“如何提出要求”与“内部如何完成”分开。调用者不必自己了解收藏表的每一个保存细节，但必须遵守约定，也必须处理对方可能返回的错误。

## 把“加入收藏”写成一份可交接的约定

下面是虚构接口的普通话版本，不需要先看代码：

| 交接项目 | 约定内容 |
| --- | --- |
| 想做什么 | 把文章 A17 加入当前账号收藏 |
| 调用方提供什么 | 文章编号A17，以及服务端能够核验的登录凭据 |
| 接收方检查什么 | 登录是否有效、文章是否存在、当前账号是否有访问权 |
| 成功意味着什么 | 该账号与A17的收藏关系已经保存；原先已收藏也不增加第二条 |
| 失败怎样区分 | 没登录、无权限、文章不存在、暂时不能保存，各自返回可识别的结果 |

前端收到成功，才按约定显示已收藏；收到登录失效，就提示重新登录；没有收到结果，则要按超时策略确认，而不是把三种情况都显示成成功。

双方约定“成功”只是已收到要求，和约定“成功”代表已完成保存，会产生不同界面行为。**接口不只约定字段，也约定这些字段和结果究竟意味着什么**。

服务端还要从可信凭据确定账号，不能让调用方填一句“用户是管理员”就获得权限。接口提供了进入能力的入口，入口后面的[权限检查](../05-reliability/18-trust.md)仍然需要执行。

## 接口和界面，有什么不同？

按钮和输入框主要给人操作；API 主要给程序使用。一个“收藏”按钮背后，可以调用加入收藏的 API，再把结果显示给人。

人能靠上下文猜意思，程序之间通常需要准确格式：文章编号放哪个位置、成功怎样表示、缺信息时怎样回复。格式不匹配，就像订单上填错栏目，对方未必能按你希望的方式处理。

## 协议是双方交换信息时遵守的规矩

如果程序隔着网络合作，还需要规定消息怎样发送、怎样确认结果。这类交流规则叫**协议**。HTTP 是网页和许多网络 API 常用的一种请求与响应协议。

可以把协议想成寄送方式，把 API 想成对方接受哪些具体订单。许多不同服务都使用同一种协议，但各自提供的能力和要求并不相同。

## 换一个模型服务，要检查哪些约定？

假设服务甲接受“正文”，直接返回摘要；服务乙要求“消息列表”，先返回任务编号，稍后才能查询摘要。两者虽然都叫摘要 API，交接并不相同。

替换时，软件要把输入整理成乙接受的形式，记住任务编号，等待并查询完成结果，最后再交给原页面。若只替换一个网址，其余仍按甲的方式读取结果，合作就接不上。协议相同，不代表能力约定也相同。

## 有接口，为什么仍然会出错？

约定清楚，只是合作的一项条件。信息可能填错，对方可能拒绝，网络也可能让你收不到回复。因此接口还要说明错误、等待限制、版本等行为。

世界模型里的接口是一条合作边：它告诉你两个部分怎样交接。它是否稳定，会直接影响[分工](../04-architecture/13-boundaries.md)和[修改带来的影响](../04-architecture/15-dependency.md)。
